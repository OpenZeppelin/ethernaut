GhostVault reinvents ERC4626 share accounting instead of using OpenZeppelin's implementation, and that's exactly how this bug keeps showing up in production: `shares = assets * totalSupply / totalAssets`, with no minimum-shares check and no virtual offset. Becoming the vault's first depositor with a tiny amount, then sending a large donation straight to the vault with a plain token transfer, sends the share price high enough that the next real deposit rounds down to zero shares. The assets don't disappear, they just aren't yours in any way the vault can prove, they inflate the value of whatever shares already exist.

This is a real, repeatedly-audited vulnerability class known as an ERC4626 inflation attack, and it's why OpenZeppelin's own ERC4626 implementation ships with a decimals offset (virtual shares and assets) by default: it makes the first-depositor share price impossible to manipulate this cheaply, since the attacker would need to out-donate the virtual offset itself. A simpler, protocol-level fix some vaults use is to require a minimum initial deposit, often burned to a dead address, so no single depositor can ever hold 100% of an empty vault's supply.

If you're building a vault, don't hand-roll ERC4626. If you have to, seed it yourself in the constructor with a small burned deposit, and never trust `totalAssets()` reads that a plain `transfer()` can move.
